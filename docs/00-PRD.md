# 第一部分 · 为什么做

## 1. 产品概述

### 1.1 一句话

Coop 是跑在你已有对话和群聊上的**超级助理**：替你读完读不过来的消息，把该你知道的变化准时、带证据和理由地提上来；发不发、怎么决定，都在你。

### 1.2 要解决的问题

集团管理者每天面对几十条在跑的线、几百条混杂的消息、一堆等他拍板的事。痛点可归为五类：

| 痛点 | 表现 |
|------|------|
| **散** | 同一件事的消息散在多个群和私聊，没有单一真相源，决策建立在残缺信息上 |
| **漏** | 该盯的事漏掉，交办出去石沉大海，重要不紧急的反复被拖 |
| **晾** | 该回的消息被淹没，重要的人被晾着，关系受损 |
| **撞** | 多条线撞期、抢同一批人或预算，冲突到爆发才发现 |
| **暴雷** | 临期才发现没进展；下属报「做完了」未必达标 |

这五类痛，管理者现在都靠**亲自去盯、去问、去开会、去揣摩**来对冲，持续烧掉他最稀缺的注意力和精力。Coop 的价值，就是把「维持把控感」这笔隐形开销降到接近零。

### 1.3 产品形态

- **输入**：你已有的私聊、群聊、群内文件和文档链接（不依赖任何你看不到的外部系统）
- **输出**：四类变化，每条带 变化 + 证据 + 置信度 + 为什么和你相关 + 建议动作
- **你的动作**：确认或修改 Coop 拟好的建议；对外发送一律经你确认

## 2. 目标用户与用户需求

### 2.1 目标用户

**主用户**：集团公司的管理者（事业部负责人、高管、创始人等）。

特征：

- 同时推进多条线，每条线涉及多个人、多个群
- 每天消息量远超个人处理能力
- 大量工作通过 IM 推进，信息分散、状态靠人记
- 既要推进事，也要维护关键关系

**延伸用户**：个人重度用户。家里的「人/事/消息」与公司的「人/事/消息」是同一套模型、不同参与方，同一引擎即可覆盖（见 [附录 B](#附录-b-引擎内部模型人事消息)）。

### 2.2 用户需求（两条线）

| 维度 | 用户要什么 |
|------|-----------|
| **事** | 正确发现该关注的事；把散在多处的事连成一张图；替我盯住、推动、完成该推进的事 |
| **回复** | 从海量消息里挑出该我回的；带上前情和证据拟好回复；敏感处把好关，我改两笔即发 |

## 3. 用户价值

管理者不会用产品的内部术语。他的痛是**把控感在流失**：事没声音了、怕漏了重要的、某个人不对劲却说不清、卡住了不知道怎么解。

Coop 把他花在「维持把控感」上的注意力和精力省下来，还给只有他能做的判断。

| 他心里其实在说 | 现状下他怎么扛（烧掉什么） | Coop 怎么让这份消耗消失 |
|--------------|-------------------------|----------------------|
| 「这件事最近没声音了，到哪了？」 | 自己去问、开会、催——烧时间，催本身还伤信任 | 没声音时替你盯着；真停滞/有风险才出声。把控感来自「我知道我会被告知」 |
| 「几十件事并行，我怕漏了重要的。」 | 靠脑子记、靠 to-do、不停切换 check | 所有事在一处被守着，只把「需要你的」顶上来，其余替你 hold |
| 「某人最近积极性不高……说不上来。」 | 模糊的不安，怕是错觉，又怕贸然找他谈错 | 把直觉变清楚：「他在这几件事上的投入和响应在下降」。低置信时只轻提示，不替你下定论 |
| 「事情好像没在正确地推进。」 | 感觉不对却找不到抓手，只能广撒网式过问 | 精准点出哪些事在空转，而不是让你全面巡查 |
| 「天天开会发消息，到底有没有实质进展？」 | 在信息洪流里分不清信号与噪声 | 每条消息已被判好「让事更明确了，还是原地打转」。你看的是进展，不是消息 |
| 「这事卡住了，我不清楚卡在哪、怎么解。」 | 召集人开会摸排，耗时且常摸不到真因 | 诊断卡点在信息还是在人，并给解法路径。摸排它做掉，决策留给你 |

> **个人用户**的痛与之对称：管理者怕的是**失控**，个人用户怕的是**辜负**——怕冷落了人、漏了答应的事、日子白过、陪家人时又走神。Coop 把「惦记着、怕漏了、怕辜负」的心理负担替他卸下来。

## 4. 产品目标

### 4.1 核心目标

替你读完读不过来的对话和消息，把**该你知道的变化**——准时、带证据和理由——提上来；让你不靠亲自盯也能拿回把控感，余力还给只有你能做的判断。

### 4.2 支撑目标

| 目标 | 说明 |
|------|------|
| 既报有进展的，也报该有进展却没动静的 | 有新消息或新进展的事提上来；长时间没按预期得到回复或更新的事也提上来 |
| 把散在多个群的同一件事连起来 | 归并成这件事的完整状态，给单一视图 |
| 每条结论都带出处和置信度 | 附上来源消息或文档，以及判断的把握程度 |
| 只在值得你知道时才出声 | 绝大多数消息不打扰你，只有产生了值得你知道的变化才提示 |
| 信息不足时先查再问 | 先查已有文档和信号，再问群，最后才问人；问之前先拟好、等你确认 |
| 让事被正确地推动 | 停滞与失控提前冒泡；该完成的推向完成，该存续的保持节奏 |

### 4.3 成功标准（方向性）

- 用户每天能在 5 分钟内处理完「该他知道的」变化
- 用户确认率（拟好建议被采纳的比例）持续上升
- 用户因「漏事 / 漏回 / 临期暴雷」产生的补救动作减少

# 第二部分 · 做成什么样

## 5. 产品原则与边界

### 5.1 三条行为规矩

你接管得越多，越需要能随时复核 Coop。它做事守三条规矩：

| 规矩 | 说明 |
|------|------|
| 每条都带证据和置信度 | 结论附上来源消息或文档，以及判断的把握程度，你能自己复核 |
| 每个判断都讲理由 | 为什么这条和你相关、为什么建议这个动作，都说清楚 |
| 对外动作都等你确认 | Coop 只拟好建议，发不发由你决定；做得越多，理由讲得越细 |

### 5.2 对人和对外的边界

- 排序和建议只依据你的目标
- 关于人只陈述观察到的行为事实，不替你下判断（说「响应变慢了」，不说「他积极性低」）
- 有把握就给建议，没把握就标明不确定，并把判断交回你
- 对外动作都等你确认后才发出
- 每次催、问都在消耗关系，措辞和频率由你掌控

### 5.3 可观测性边界：每个判断都带「看得见的程度」

产品的智能不是「它什么都知道」，而是**它知道自己知道什么、不知道什么，并让你低成本补上缺口**。据此，每条判断落在三条「可观测性带」之一，行为不同：

| 可观测性带 | 例子 | Coop 的行为 |
|-----------|------|--------------|
| **看得见 · 高置信** | 合同 9 天没动（时间戳）；你答应周五交 X（消息抽取） | 静默托管，只在阈值被突破时才出声 |
| **看不全 · 低置信** | 某人回复变短变慢——可能疏远，也可能没事 | 不断言、不行动；给你一键确认（「你注意到了吗？」），把你变成传感器 |
| **看不见 · 不可观测** | 没说出口的顾虑、走廊里的对话、你的直觉 | 明确承认看不见；用最低成本请你「存入」（如 10 秒语音），并把你存入的信号当一等公民 |

这三带同时是投入顺序与竞争壁垒：看得见是高可靠基本盘；看不全是差异点；看不见是护城河——竞品也看不见，谁让「存入」最便宜谁赢。

## 6. 核心能力模型

### 6.1 针对「事」：五阶段

```
发现事 → 建关联图 → 关注 → 推动 → 完成
```

| 阶段 | Coop 做什么 |
|------|------------|
| **发现事** | 从消息流中识别出值得成为「事」的候选；检出目标 / 标准 / 期限是否清楚 |
| **建关联图** | 把同一件事散在多个群、多个人的消息归并；建立事与人、事与事的关联 |
| **关注** | 用户确认关注后，持续维护这件事的最新状态；侦测该有进展却没动静的情况 |
| **推动** | 发现缺口 → 派生子事 → 拟好找谁 + 怎么说 → 等你确认发出（详见第 7 章） |
| **完成** | 跟踪回复是否有效闭合子事；有效则更新母事；报完成时按标准验收 |

### 6.2 针对「回复」：分流、备稿、把关

| 能力 | 说明 |
|------|------|
| **分流** | 按「谁 · 多重要 · 要不要你回」从海量消息中挑出该你处理的 |
| **备稿** | 附上相关事的前情和证据，拟好一版回复 |
| **把关** | 敏感处给多版措辞 + 风险标注；明确提示「建议你亲自定」 |

## 7. 统一回路：补缺口派生

「盯进展」不是单个动作，而是一条通用回路。所有「推动」类动作都走同一条回路，只是被不同的「缺口」触发。缺口来源只有两个：**事的健康度** 与 **人通道的状态**。

### 7.1 回路五步

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1. 侦测 Sense | — | 可观测信号触发：发现某个缺口 |
| 2. 派生 Derive | — | 生成一个要找人推进的子事 |
| 3. 拟稿 Draft | — | 建议对象 + 内容（找谁 · 怎么说） |
| 4. 你确认 · 发出 | — | 用户确认后才发出 |
| 5. 收敛 Close | — | 回应是否有效闭合 → 完成子事 + 更新母事 |

**实例（催更新）**：侦测「churn 数据：增长群 2 天没更新」→ 派生子事「问增长群」→ 拟稿「找增长负责人 · 问『churn 口径今天几点能出』」→ 你确认后发出 → 跟踪回复延迟和内容 → 有效则完成子事并更新母事；超时/无效则升级。

### 7.2 事侧：推进型事的 7 类缺口

| 缺口类型 | 触发信号（可观测） | 派生子事 | 闭合判据 |
|---------|-------------------|---------|---------|
| 缺信息 · 沉默 | 该更新却 N 天无新消息 / 无动静 | 催更新（盯进展） | 拿到有效进度更新 |
| 缺明确 | 目标 / 范围 / 标准 / 负责人 / 期限不清 | 求澄清 | 关键字段被补全 |
| 缺推力 | 被前置依赖或某人阻塞 | 推依赖 · 解卡 | 阻塞解除、可继续 |
| 缺决断 | 卡在需要拍板才能继续 | 请决策（拟好选项） | 拍板产出，事可继续 |
| 有碰撞 | 撞期 / 抢资源 / 两方口径不一 | 协调对齐 | 冲突消解、口径一致 |
| 临期限 | deadline 临近且未达成 | 赶节点 · 提醒 | 按期完成或重新排期 |
| 待验收 | 声称完成但未确认 | 验收闭环 | 确认确实 done |

### 7.3 人侧：人通道的 3 类缺口

| 缺口类型 | 触发信号（可观测） | 派生子事 | 闭合判据 |
|---------|-------------------|---------|---------|
| 通道冷却 | 触达冷却 ≥ N 天，长期无互动 | 维系触达 | 重新建立联系 |
| 承诺悬空 | 答应了某事，到点没动作 | 追承诺 | 兑现或重新约定 |
| 信号异常 | 响应速度 / 语气明显变化 | 关心 + 择时修复 | 状态回暖 / 找到症结 |

> 「追承诺」与「催更新」是同一回路的两个入口：一个从**事**进（事没动静），一个从**人**进（人欠你的没兑现）。

### 7.4 横切：拟稿里要替你决定的三件事

| 维度 | 说明 |
|------|------|
| 找谁（对象） | 人-事匹配：谁有答案、谁是瓶颈、谁能拍板 |
| 何时（择时） | 读人状态，挑对方最可能积极响应的时机 |
| 怎么说（措辞） | 按信任 / 情绪 / 关系成本给措辞 + 置信度 |

### 7.5 收敛与升级

每个派生子事必须有明确的闭合判据，靠两路信号判断：**回复延迟**（对方多久没回）与**内容质量**（回复是否足以闭合）。

| 结果 | 动作 |
|------|------|
| 有效 | 完成子事 + 把更新回收进母事 |
| 无效 / 超时 | 升级：换人、换措辞、或交还给你定 |

子事永远向母事汇报，不留悬空。

### 7.6 推进型事 vs 存续型事

| 类型 | 价值在 | 缺口表现 | 闭合判据 |
|------|--------|---------|---------|
| 推进型（telic） | 结果 | 没进展、被卡、临期 | 事完成 / 节点达成 |
| 存续型（atelic） | 过程 | 太久没投入、温度下降 | 恢复节奏 |

第 7.2 的 7 类缺口主要对应推进型事。存续型事（如家人陪伴、关系维系）的缺口是「太久没投入」，人侧的「维系触达」就是它的盯防。

## 8. 派生治理规则

子事闭合 ⇒ 母事推进，这个推断每多一跳就乘一次正确率 p。顶层状态可信度 ≈ p^层数，因此必须治理派生深度——否则「替你盯、你只看顶层」的承诺会失效。

### 8.1 关键数字

| 指标 | 值 | 说明 |
|------|-----|------|
| 默认呈现 | 2 层 | 主事 + 推进它的子事，最优 |
| 自动派生硬顶 | 3 层 | 子事自己停滞时惰性展开 |
| 活跃叶子数 / 顶层事 | ≤ 7 | 一眼能扫完的 open frontier |
| 绝对红线 | 5 层 | 含人工手动，越线强制提示重构 |

### 8.2 顶层可信度 vs 派生层数（示意，p≈0.85）

| 派生层数 | 顶层可信度 | 含义 |
|---------|-----------|------|
| 2 层 | ~0.72 | 理想 |
| 3 层 | ~0.61 | 可接受：子事自己停滞时惰性展开 |
| 4 层 | ~0.52 | 已近抛硬币 → 应横向拆成并列事 |
| 5 层 | ~0.44 | 红线：越线强制重构 |

### 8.3 五条治理规则

1. **自动派生硬顶 3 层 · 默认呈现 2 层**：第 3 层折叠、按需展开
2. **第 3 层惰性生成**：仅当某子事自己停滞、需要它自己的补缺口回路时才生成
3. **想触第 4 层 → 不 nest，报警**：提示「顶层事框错了高度」，建议横向拆成并列 peer（你确认后执行）
4. **复杂度阀门挂在活跃叶子数上**：每个顶层事 open frontier ≤ 7 + 限扇出，而非纯卡深度
5. **5 层为绝对红线**：越线即强制提示重构

> 想往更深 nest 时，往往是顶层事「框错了高度」。正确做法是横向拆成并列事——用关联图横向吸收复杂度，而不是把树越拉越长。「收敛派生」与「建关联图」是互补的一对。

# 第三部分 · 具体要什么

## 9. 核心场景（P0/P1/P2）

优先级：**P0** 核心，MVP 必须覆盖；**P1** 重要，首发应覆盖；**P2** 完善，后续迭代。

场景统计：

| 维度 | P0 | P1 | P2 | 合计 |
|------|----|----|----|----|
| 事 | 4 | 5 | 3 | 12 |
| 回复建议 | 3 | 4 | 3 | 10 |
| **合计** | **7** | **9** | **6** | **22** |

### 9.1 维度一 · 事：替你盯住、推动、完成

**P0 · 核心**

| 场景 | 原有问题（现状代价） | Coop 的体验 |
|------|---------------------|------------|
| 晨起千头万绪：今天该抓什么 | 凭记忆 + 直觉排序，时间被喊得响的事占满，重要不紧急的反复被漏 | 按「对你目标的杠杆 × 时效」排出今日该抓的 3–5 件，并说明为什么 |
| 交办出去，石沉大海 | 不催就拖、催多了伤关系；要么反复惦记，要么忘到暴雷 | 侦测「该更新没更新」→ 拟好找谁 + 怎么催，你确认即发，回收答复判断真假进展 |
| 临期暴雷：截止前才发现没进展 | deadline 前才知道来不及，已无法补救；全靠自己卡日历 | 临期主动预警 + 拟好赶节点动作，把暴雷提前到还能救的时点 |
| 同一件事散在多个群和私聊 | 没有单一真相源，决策建立在残缺信息上；自己当人肉聚合器 | 把关联的人 / 消息 / 文档自动连成一张图，给你单一视图 |

**P1 · 重要**

| 场景 | 原有问题（现状代价） | Coop 的体验 |
|------|---------------------|------------|
| 一句话安排，被理解跑偏 | 执行偏了方向，几天后才发现、返工；写细累、含糊又返工 | 派生时即检出目标/标准/期限不清，先替你把澄清问题问对人，明确后才推进 |
| 多条线撞期，抢同一批人或预算 | 冲突到爆发才发现，你被动当救火队长兼裁判 | 提前侦测撞期 / 抢资源 → 拟好协调方案 + 该找谁定，爆发前摁住 |
| 决策卡在你这，下面一堆人等 | 不知道哪个最该先定，信息又不全，拍板一拖全线停 | 把待你决策的事按影响排序，附齐选项 + 利弊 + 证据，你只做选择 |
| 「做完了」是否达标 | 下属报完成不放心，验收走过场，或自己反复复查 | 报完成即派生验收，按你定的标准核对再 close |
| 事被某人或某环节卡住 | 不知道卡在谁那、卡了多久，发现时已经误了不少 | 定位阻塞点 + 卡了多久，拟好「推动谁」的动作，解卡后自动续推 |

**P2 · 完善**

| 场景 | 原有问题（现状代价） | Coop 的体验 |
|------|---------------------|------------|
| 例行 / 周期性事项不漏 | 靠记忆推例行事，节奏一乱就漏 | 按节奏自动起事 + 提醒，到点没动就转成催进展 |
| 潜在风险事项主动浮现 | 合规 / 舆情 / 人事的风险冒头时没人提，等爆发才知 | 扫描弱信号，把可能成事的风险提前浮现给你看一眼 |
| 事完成后的复盘沉淀 | 事一完成就过去了，经验和决策依据没留存，下次重复踩坑 | close 时自动归纳过程 + 关键决策，沉淀成可检索的复盘 |

### 9.2 维度二 · 回复建议：替你分流、备好、把好关

**P0 · 核心**

| 场景 | 原有问题（现状代价） | Coop 的体验 |
|------|---------------------|------------|
| 一早 300+ 未读，重要的被淹 | 回错优先级、漏回关键的人；逐条人脑分流，又累又会漏 | 按「谁 · 多重要 · 要不要你回」分流，把要你处理的拎出来排序 |
| 对方追问，得翻半天前情才能回 | 没上下文不敢回 → 回复一拖再拖 | 自动附上相关事的前情 + 证据，并拟好一版回复，你改两笔即发 |
| 忙忘了，晾着重要的人 | 关系受损、对方觉得不被重视；靠红点 + 记忆，重要的反被拖最久 | 盯响应延迟，对关键关系提醒，并备好「先稳住」的轻回复 |

**P1 · 重要**

| 场景 | 原有问题（现状代价） | Coop 的体验 |
|------|---------------------|------------|
| 要回一条敏感 / 高风险消息 | 涉裁员 / 纠纷 / 对外口径，一句说错引发更大问题，迟迟不敢回 | 给 2–3 版措辞 + 风险标注 + 置信度，敏感处明确提示「建议你亲自定」 |
| 某核心高管回复变冷、变慢 | 察觉不到积极性下滑，等提离职才知道 | 从响应速度 / 语气捕捉异常 → 低置信预警 + 建议何时、以什么由头关心 |
| 关键关系大半年没主动联系 | 关系自然冷却，真要用时使不上劲；想起来才偶尔维系 | 侦测触达冷却 → 挑对时机 + 由头拟好一条问候，你确认即发 |
| 同一件事要同步给多人 / 多场景 | 口径一不一致全靠自己手动重写，费神又容易出入 | 拟好统一口径的多版本（对上 / 对下 / 对外），一致同步、措辞各自得体 |

**P2 · 完善**

| 场景 | 原有问题（现状代价） | Coop 的体验 |
|------|---------------------|------------|
| 开会前后 | 会前没空准备背景；会后待办散落，跟进全凭记忆 | 会前自动备 brief，会后把决议拆成事 + 待办并自动跟进 |
| 别人答应过你的事 | 没人帮你记，到点没兑现你也想不起来 | 抽取「谁答应你什么、何时」，到点没动自动转成追承诺 |
| 对上 / 对下 / 对外 语气切换 | 同一意思换个对象就要重新拿捏语气，很耗神 | 按对象自动切换语气与详略，你审一眼即用 |

## 10. 理想态：稳定运行态

### 10.1 Coop 的四种运行模式

| 模式 | 节奏 | 行为 |
|------|------|------|
| **持续在做** | 被动 · 不打扰 | 读你的私聊和群聊；把消息归并到人和事，维护最新状态；绝大多数时候不出声 |
| **何时出声** | 输出门槛 | 只在产生了值得你知道的变化时；每条带完整五要素；新发现类、人变化类门槛更高 |
| **怎么补盲区** | 主动 · 有分寸 | 信息滞后/不明确时建议去问谁或哪个群；你确认后才发；补信息顺序：查文档和信号 → 问群 → 最后问人 |
| **怎么懂你** | 学习 | 从你盯/静音/采纳/忽略里学偏好；偶尔问一下你的优先级，校准什么算相关 |

### 10.2 用户理想的一天

1. **打开 Coop**：看到今日该抓的 3–5 件事（按杠杆 × 时效排序），以及自上次查看以来的变化
2. **处理变化**：每条带证据和理由；需对外动作的，Coop 已拟好找谁 + 怎么说，你确认或改两笔即发
3. **处理消息**：该你回的已排好序，附上相关事的前情；敏感处有多版措辞和风险标注
4. **其余时间**：Coop 静默盯着；该有进展却没动静的、临期的、撞期的，主动提上来
5. **你的动作**：判断和拍板；Coop 把材料准备到你面前

## 11. 输入与输出

### 11.1 输入

| 来源 | 说明 |
|------|------|
| 私聊 + 群聊 | 尤其项目群 |
| 群内文件 / 文档链接 / 纪要 / 转发 / 截图 | 从消息中抽取 |
| 你已关注的事 / 人 / 项目 | 显式关注 + 反馈历史 + 学到的偏好 |

来源就是你已有的对话——不依赖任何你看不到的外部系统。

### 11.2 输出 · 四类变化

只给变化，不堆看板。每条包含：**变化 + 证据 + 置信度 + 为什么和你相关 + 建议动作**。

| 类型 | 内容 |
|------|------|
| ① 已关注事项的变化 | 推进了 / 没声音了 / 变复杂了 / 风险升高 / 有人给了新承诺 |
| ② 衍生子事项的变化 | 长出新分支 / 子事项开始影响母事 / 没人接的子事项 |
| ③ 新发现的候选事项 | 你还没明确关注、但可能值得——低置信，可一键确认「要我帮你盯吗」 |
| ④ 关注的人的变化 | 只讲行为、带证据、不贴标签（说「响应变慢了」，不说「他积极性低」） |

## 12. 信息架构与界面

界面遵循「只呈现需要你的」原则，收敛为一主一次两个面：

| 界面 | 角色 | 说明 |
|------|------|------|
| **Now（主屏）** | 唯一主屏，取代收件箱 | 极短列表，只列「现在需要你的那几件事」，每项标注「为什么需要你」。动作随事一起出现，不做独立目的地。要深度时就地展开 |
| **信任审计（次级）** | 让你复核 Coop | 回答「我看到了什么、多确定」：输入被归并到哪些事、每条判断的置信度。取代传统「待回消息」列表，避免变成换皮收件箱 |

Now 主屏每项的四种「为什么需要你」：

| 标签 | 含义 |
|------|------|
| 需要你拍板 | 看得见、已就绪的决策 + 一版草稿 |
| 需要你判断 | Coop 没把握——给出看法，把判断权交回你 |
| 需要你当传感器 | 「这是不是在酝酿？」一键确认 |
| 需要你亲自出面 | 只有你能做的那个动作 |

> 界面上尽量不出现引擎内部术语（事树、通道、态等）。这些是实现语言，不是用户语言。

**诚实 vs 幻觉**：不要断言 Coop 观测不到的原因。
- ✗ 不诚实：「并购卡在『对方法务有顾虑』」（断言看不到的原因）
- ✓ 诚实：「这件事 9 天没动，在它这个阶段不寻常，我看不出原因。要不要标记？[我去问 owner] [我知道为什么 →]」

## 13. AI 能力栈

支撑上述产品的底层 AI 能力（标注与现有 eval 分类树的关系）：

| 能力 | 说明 / 分类关系 |
|------|----------------|
| 输入 → 事归并（attribution） | 把每条消息/文件归到对应的事，并标注涉及的人 |
| 态估计 | 判断事的模糊/明确程度 + 推进型/存续型分类 |
| 瓶颈诊断 | 判断卡点在信息还是在人 |
| 人通道状态推断 | 从行为信号推断信任/情绪/响应变化；第三方推断高敏感，需保守 |
| 自递归 rollup | 子事闭合后向母事汇总更新 |
| 落差检测 | 参与方口径不一致的识别（近 L3.24 意图理解） |
| 推进路径生成 + 草稿 | 生成找谁+怎么说的建议稿（扩 L3.26 草稿质量 / L3.34 推荐） |
| 置信度校准 + 弃权移交 | 所有判断带置信度；低置信弃权、交回用户（贯穿所有能力的不变式） |
| 承诺 / 危机信号抓取 | 从消息抽取承诺与风险信号（扩 L3.54 危机检测） |

## 14. 非目标

以下不在 Coop v1 范围内：

| 非目标 | 原因 |
|--------|------|
| 替代 IM / 邮件客户端 | Coop 读已有对话，不做消息收发 |
| 项目管理 / OKR 工具 | 不做看板、甘特图、OKR 填报 |
| 自动对外发送（不经用户确认） | 每次对外动作都消耗关系，必须经用户确认 |
| 替用户下判断（尤其关于人） | 只陈述行为事实，判断交回用户 |
| 依赖外部系统（ERP / CRM / BI） | 输入来源限于用户已有的对话和群聊 |
| 通用 AI 聊天 / 问答 | 输出收紧为四类变化，不是通用对话 |

## 15. 关键风险

| 风险 | 说明 | 缓解 |
|------|------|------|
| 幻觉式感知 | 断言观测不到的原因，误导用户 | 严守可观测性带；看不见就明说，不猜 |
| 第三方人状态推断 | 对第三人的敏感推断带来隐私/伦理风险 | 只陈述行为事实、不贴标签；明确隐私边界；高敏感场景保守 |
| 打扰过度 | 出声太频繁，用户失去信任 | 严格输出门槛；绝大多数消息静默；从用户反馈学门槛 |
| 关系损耗 | 代发的催/问消耗用户的人际资本 | 所有对外动作先经确认；控制频率；给关系成本提示 |
| 自动收敛失真 | 派生过深导致顶层状态不可信 | 派生治理（第 8 章）：硬顶 3 层、活跃叶子 ≤7、红线 5 层 |

## 附录 A · 术语表

| 术语 | 定义 |
|------|------|
| 事 | 用户关注的一个推进或存续单元，有状态、参与方、进展 |
| 子事 | 从母事派生出的、要找人推进的具体动作（如催更新、求澄清） |
| 变化 | Coop 输出给用户的一条信息：某事或某人发生了什么 |
| 置信度 | Coop 对这条判断的把握程度（高 / 中 / 低） |
| 可观测性带 | 一条判断能被看见的程度：看得见 / 看不全 / 看不见 |
| 拟稿 | Coop 拟好的建议：找谁 + 说什么 + 理由 |
| 确认 | 用户审阅拟稿后同意发出或修改后发出 |
| 收敛 | 子事得到有效闭合（拿到有效回复 / 完成验收），更新回母事 |
| 推进型事 | 价值在结果的事（如合同回签、项目上线） |
| 存续型事 | 价值在过程的事（如家人陪伴、关系维系） |
| Now | 唯一主屏，只列现在需要用户的那几件事 |
| 信任审计 | 次级界面，展示 Coop 看到了什么、多确定 |

## 附录 B · 引擎内部模型（人/事/消息）

以下是引擎内部的组织方式，**不作为用户语言出现在界面上**。产品把「身份 / 主线 / 关系 / 时间」等旧框架坍缩为三个本体：

| 本体 | 角色 | 承载 |
|------|------|------|
| **人 People** | 通道 | 角色与关系；主观状态（信任 / 情绪-负荷 / 认同）；参与的事及各自角色；交付画像（能扛模糊指令 vs 只能执行明确指令）。护栏：人是目的，不是被榨取的通道 |
| **事 Matters** | 骨架 · 注意力单位 | 态（模糊 ⇄ 明确）+ 类型（推进 / 存续）；参与方；事树位置（母/子）；瓶颈诊断（信息 vs 人）；下一步 / deadline |
| **消息 Inputs** | 燃料 | IM / 邮件 / 会议转写 / 文件 / 文档；不是注意力单位，而是「事的状态变更流」；每条归并到事、标人、标态变化、标承诺/危机 |

一句话架构：**消息是燃料 → 经由人这条通道 → 推动事这副骨架（从模糊走向明确或保持存续）**。身份是根事；「今日」是「需你介入」的视图；「复盘」是对根事的一种收敛动作。

同一引擎跑个人 ↔ 组织：家里和公司都是同一套人/事/消息，切换的只是参与方构成。
